  • 리플렉션: 셀마다 하던 필드 조회를 컬럼별로 한 번 만드는 함수 캐시로 바꿔 반복 조회를 줄였습니다.

  • 알림: 조회 행이 1,000건을 넘는 대용량 작업은 시작 시점에 Slack으로 알렸습니다.
  • 테스트: Fetcher·조립기·전략·검증기·서비스를 계층별 단위 테스트로 검증했습니다.

AI와 협업한 방식제안은 AI가, 판단과 검증은 제가

  1. 요구사항 구조화: 기획서를 API·DTO·검증·테스트 단위로 나눴습니다.
  2. 대안 비교: SXSSF의 flush·임시 파일 관리, 청크 단위 조회, HTTP 스트리밍 응답, ECS 요청 시간 제한을 놓고 장단점을 따졌습니다. 그중 SXSSF 스트리밍 쓰기와 청크 단위 조회를 적용했습니다.
  3. 구현과 리팩터링: 확정한 구조로 계층별 코드를 작성하고 다듬었습니다.
  4. 검증: 반영한 코드는 계층별 단위 테스트로 확인했습니다.
  5. 채택·보류 판단: 기존 구조와 운영 환경에 맞는 제안만 반영했고, 일부 리팩터링 제안은 보류했습니다.

실패 건이 어떤 상태로 끝났는지부터 분류해, 상태마다 처리 방법을 정했습니다.

문제실패한 주문·송장이 다시 처리되지 않았습니다

외부 OMS·쇼핑몰과 주문·송장을 주고받다 실패한 건이 그대로 쌓였습니다. 셀러가 문의하면 제가 한 건씩 확인해서 다시 보냈습니다. 연동사마다 로직이 따로 흩어져 있어서, 고칠 때마다 다른 연동사에서 같은 문제가 다시 나왔습니다.

목표패치 대신, 실패가 상태별로 처리되는 구조

같은 증상에 패치를 덧대지 않고, 실패 건이 사람 손을 거치지 않고 상태별로 처리되게 하는 것이 목표였습니다. 연동사가 늘어도 같은 흐름에 끼워 넣을 수 있어야 했습니다.

설계와 구현공통 흐름은 하나로, 연동사 차이는 따로

  • 구조: 공통 연동 서비스가 조회·분류·재전송 흐름을 맡고, 연동사별 서비스는 각 연동사의 요청과 응답만 처리합니다.
  • 응답 코드: 연동사마다 다른 응답 코드를 Enum으로 정리해, 같은 기준으로 상태를 판단하게 했습니다.
  • rate limit: 같은 셀러의 요청이 연달아 나가면 사이에 5초 딜레이를 넣었습니다.
  • 재전송 한도: 최대 3회까지 자동 재전송하고, 3회 모두 실패한 건은 수동 재전송 API로 넘겼습니다.
  • 중복 전송: 한 배치 안에서 연동 주문·출고 주문 식별자 기준으로 중복을 걸러, 같은 건이 두 번 나가지 않게 했습니다.
  • 수집 데이터 정제: 주문을 수집할 때 공백·이모지 제거를 공통으로 처리했습니다.
  • 정리: 쓰지 않는 코드 약 750줄과 불필요한 트랜잭션을 걷어냈습니다.

문제정산 한 번에 10분, 그동안 다른 운영자는 기다렸습니다

정산 프로시저는 한 번 실행에 최장 10분이 걸렸습니다. 순차 처리 구조라 그동안 다른 운영자는 정산을 진행할 수 없었습니다. 가장 무거운 조회는 100만–1억 row 규모의 테이블 여러 개를 JOIN하는 쿼리로, 30초가 걸렸습니다.

목표운영팀이 정산을 기다리지 않게

정산 담당으로서 운영팀의 정산 대기 시간을 줄이는 것이 목표였습니다. 지원 종료를 앞둔 MySQL 5.6도 함께 정리해야 했습니다.

설계와 구현쿼리와 DB 버전, 두 가지를 손봤습니다

  • 느린 실행: 실행계획을 분석해 풀 스캔과 인덱스 누락을 찾았습니다. 조회와 조인에 자주 쓰는 컬럼에 복합 인덱스를 추가하고, 조인절과 WHERE절을 다시 썼습니다.
  • 구버전 DB: AWS RDS의 MySQL 5.6 지원 종료에 맞춰, 범위와 위험을 시니어에게 먼저 설명해 권한을 받고 8.0 전환을 진행했습니다.
  • 접속 분리: 4개 서버(웹·배치·택배사 연동·인터페이스)의 local·dev 접속 대상을 운영 클러스터에서 개발 전용 클러스터로 분리하고, 웹 서비스는 MySQL 8에 맞춰 Hibernate를 올렸습니다(2023.02).

30s → 3ms

가장 무거웠던 단일 쿼리가 30초에서 3ms로, 정산 프로시저 단일 실행이 최장 10분에서 1분 이내로 줄었습니다. 순차 처리 구조는 그대로였지만, 다른 운영자가 기다리는 시간도 그만큼 줄었습니다.

기준: 30s → 3ms는 MySQL 8.0에서 복합 인덱스 적용 전후 같은 쿼리의 실행 시간 · 10분 → 1분은 프로시저 단일 실행 처리 시간(인덱스·쿼리 개선 효과)

4개 서버 로깅을 Datadog 기준으로 개편

모든 메서드에 남기던 로그를, 요청 하나를 따라갈 수 있는 로그로 바꿨습니다.

2024.06 – 2024.10
역할 담당
웹배치택배사 연동인터페이스 Spring AOPLogbacklogstash-encoderMDC

문제로그는 많은데 찾을 수가 없었습니다

Datadog을 도입했지만 로그가 텍스트라 검색과 파싱이 어려웠습니다. 연동 서버는 AOP로 스케줄·컨트롤러·서비스·태스크·매퍼의 모든 메서드에 START/END 로그를 남겨서, 로그량은 많은데 장애가 나도 요청 하나의 흐름을 따라가기 어려웠습니다.

목표많이 남기는 로그가 아니라 따라갈 수 있는 로그

웹·배치·택배사 연동·인터페이스 4개 서버의 로그를 Datadog에서 검색할 수 있게 하고, 장애가 나면 요청 하나의 흐름을 따라갈 수 있게 만드는 것이 목표였습니다.

Before 개념 예시 
// 5개 계층의 모든 메서드
@Around("모든 Schedule·Controller·
         Service·Task·Mapper 메서드")

[START] : 'XxxService.search()'
[END  ] : 'XxxService.search()'

호출마다 두 줄씩, 텍스트로 쌓였습니다.

After 개념 예시 
// 요청·응답 경계에서만
@Around("@RestController 메서드
         (헬스체크 제외)")

MDC.put("traceId", UUID)
→ Request  : 인자
→ Response : 상태 코드, Body
// JSON 한 줄 → Datadog 파싱

요청 단위로 남고, traceId로 묶입니다.

설계와 구현서버마다 무엇을 바꿨나

  • 4개 서버 공통: logstash-logback-encoder로 JSON 구조화 로그로 전환했습니다.
  • 연동 서버: 전 메서드 로깅을 @RestController 요청·응답 로깅으로 바꾸고, MDC에 요청별 traceId를 넣었습니다. HTTP 요청 로깅 필터를 따로 만들어 메서드·URI·파라미터를 남기고, 헤더·인증값이 찍히던 디버그 로그를 지웠습니다.
  • 배치 서버: 기존 AOP 로깅을 컨트롤러 요청과 태스크 시작·완료 기준으로 다시 짜고, 29개 파일에 흩어진 개별 로그와 레벨을 정리했습니다.
  • 웹 서비스: 불필요한 로그를 걷어내고, 연동사별 OMS 로그를 정비했습니다.
  • 적용 중 문제: local에서는 되는데 prod에서는 적용되지 않았습니다. 바로 고치지 않고 먼저 롤백한 뒤 원인을 찾아 다시 적용했습니다.

전 메서드 로깅을 걷어내 수집량이 크게 줄었고, 장애가 나면 traceId 하나로 그 요청의 흐름을 따라갈 수 있게 됐습니다.

추적 ID는 가장 바깥인 필터에서 만들고, 요청이 끝나면 반드시 지워야 했습니다. 당시에는 AOP에서 만들어서 필터 로그에는 ID가 없었고, MDC.clear()도 빠뜨렸습니다.

지금 다시 만든다면 필터에서 traceId를 만들어 응답 헤더로 돌려주고, try/finally로 MDC를 정리하겠습니다. 요청·응답 Body는 통째로 남기지 않고 마스킹과 크기 제한을 두겠습니다. Body 전체를 남기면 비용이 늘고 개인정보 문제가 생기기 때문입니다.

출고 취소를 프로시저에서 Java 서비스로

취소 로직을 보이는 곳으로 꺼내 단계별로 검증했고, 남은 한계도 함께 적었습니다.

2022.12
역할 담당
Spring@TransactionalMyBatisMySQL

문제취소가 겹치면 중간 상태가 어긋났습니다

출고 취소는 DB 취소 프로시저 2개 안에 있었습니다. 같은 출고에 취소가 겹치면 회차·주문·상품 사이의 상태가 어긋났는데, 로직이 프로시저 안에 있어 어디서 어긋나는지 보기 어려웠습니다.

목표보이게 꺼내고, 한 번에 맞게

취소 로직을 프로시저에서 코드로 꺼내 어디서 상태가 어긋나는지 보이게 하고, 회차·주문·상품 상태가 함께 바뀌게 하는 것이 목표였습니다.

설계와 구현프로시저를 걷어내고 단계를 나눴습니다

  • 취소 프로시저를 제거하고, 회차 전체 취소와 주문 단위 취소를 Java 서비스 메서드로 나눴습니다.
  • 갱신 전에 회차·주문·상품 단계별 상태를 조회해, 이미 취소됐거나 출고가 끝난 건은 각각의 오류 코드로 거부했습니다.
  • 서비스에 클래스 단위 @Transactional을 걸어, 중간에 실패하면 회차·주문·상품 갱신이 함께 롤백되게 했습니다.
  • 배포 뒤에는 상품 단위 중복 취소 차단, 출고 신청 중 취소 오류와 빈 IN () 조건 방지, 신청 도중 이탈한 건 처리를 핫픽스로 보완했습니다.
당시 구현 · 조회 후 갱신 개념 예시 
-- 1) 상태를 먼저 조회해 검증
SELECT status FROM out_order WHERE id = ?;
-- 이미 취소·완료면 예외

-- 2) 사용 중인 행만 조건으로 갱신
UPDATE out_order SET status = '취소'
 WHERE id = ? AND 사용여부 = 'Y';
-- 갱신 0건이어도 그대로 진행

검증과 갱신이 두 단계로 나뉘어, 동시에 들어온 요청이 둘 다 검증을 통과할 수 있었습니다. 갱신 건수가 0이어도 실패로 보지 않았습니다.

지금이라면 개념 예시 
-- 현재 상태를 갱신 조건에 건다
UPDATE out_order SET status = '취소'
 WHERE id = ? AND status = ?;

-- 0건이면 예외 → 트랜잭션 전체 롤백

확인과 갱신을 한 문장으로 합치고 갱신 건수를 확인해, 동시에 온 요청 중 하나만 상태를 바꾸게 하겠습니다.

중복 취소 거부·부분 갱신 방지

이미 취소·완료된 건을 거부하고 회차·주문·상품 갱신을 한 트랜잭션으로 묶어, 순서대로 들어온 중복 취소와 부분 갱신을 막았습니다.
